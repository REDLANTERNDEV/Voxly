# Music Bot Design

Status: ready for implementation. Vocabulary follows [CONTEXT.md](../../CONTEXT.md).
Architecture decisions: [ADR-0001](../adr/0001-music-bot-is-a-mesh-peer.md),
[ADR-0002](../adr/0002-werift-for-the-bot-webrtc-stack.md).

## Problem Statement

People using Voxly to talk to friends have no way to listen to music together. They
either leave Voxly for another app, or one person shares their screen purely to
broadcast audio — which wastes bandwidth, ties up that person's machine, and gives
nobody else any control over what plays.

## Solution

Each Voxly server gets a Music bot: a member that is visibly not a person, which joins
a voice room on request and plays audio into it.

Someone already in a voice room searches for a song by name or pastes a YouTube link.
The Music bot joins that room and starts playing. A panel in the voice room shows the
Queue, who requested each Track, and controls to pause, resume and skip. Anyone in the
room can use them, and a Set log shows who did what so the actions are attributable.
When everyone has left for five minutes, the Music bot leaves and forgets everything.

Because Voxly's voice architecture is peer-to-peer with no central media server, the
Music bot is a real WebRTC peer rather than something the Voxly server mixes. It runs
as its own process and connects to each Listener the same way people connect to each
other.

## User Stories

### Starting playback

1. As a member in a voice room, I want to search for a song by name, so that I can play music without leaving Voxly.
2. As a member in a voice room, I want to paste a YouTube link, so that I can play a specific Track I already found.
3. As a member searching by name, I want several results shown with the closest match already selected, so that I can accept the obvious answer instantly but still choose a different one when the top result is a cover or an hour-long mix.
4. As a member, I want the Music bot to Summon itself when I add the first Track, so that starting music is one action rather than two.
5. As a member who is not in any voice room, I want the playback controls to be unavailable, so that I cannot start music in a room I am not listening to.
6. As a member, I want to add a Track while another is playing, so that queueing does not interrupt what everyone is hearing.

### Listening

7. As a Listener, I want to hear music alongside people's voices, so that we can talk while listening.
8. As a Listener, I want my own volume control for the Music bot, so that I can make music quieter than voices without changing what anyone else hears.
9. As a Listener, I want the music to reach me at the same quality it reaches everyone else, so that nobody is hearing a degraded version.

### The Queue

10. As a member, I want to see the Queue in playing order, so that I know what is coming.
11. As a member, I want to see which Track is currently playing, distinguished from those waiting.
12. As a member, I want to see the Requester of each Track, so that I know whose song is playing.
13. As a member, I want to see each Track's length, so that I can tell how long until mine plays.
14. As a member, I want to remove a Track I can see in the Queue, so that a mistaken addition does not have to be waited out.
15. As a member, I want the Queue to be identical for everyone in the room, so that we are not looking at different lists.

### Controls

16. As a member in the voice room, I want to pause playback, so that we can talk without music over the top.
17. As a member, I want to resume playback, so that we continue from where we paused rather than restarting.
18. As a member, I want to skip the current Track, so that we can move past something nobody wants.
19. As a member, I want two people pressing skip at the same moment to skip only one Track, so that a coincidence does not cost us a song.
20. As a member, I want my action to be rejected cleanly if it is no longer valid, so that the interface never shows me a state that is not real.

### The Set log

21. As a member, I want to see that someone skipped a Track, so that I understand why the music suddenly changed.
22. As a member, I want to see who added each Track, so that actions in a shared room are attributable.
23. As a member, I want the Set log to disappear when the Music bot leaves, so that yesterday's activity does not clutter today's panel.

### Lifecycle

24. As a member who reloaded the page, I want the Queue still to be there when I come back, so that a refresh does not destroy the evening's music.
25. As the last person leaving a voice room, I want the Music bot to leave shortly afterwards, so that it is not playing to an empty room.
26. As a member returning within the Grace period, I want the music still playing, so that a brief disconnection is invisible.
27. As a member, I want the Music bot to leave when the Grace period expires, so that it does not sit in an empty room indefinitely.

### The Music bot as a member

28. As a member looking at the voice room or the member list, I want the Music bot clearly marked as a Bot, so that I do not mistake it for a person.
29. As a server owner, I want the Music bot excluded from member counts, so that my member list reflects actual people.
30. As a server owner, I want to mute the Music bot the same way I mute anyone, so that I can stop the music using controls I already know.
31. As a server owner, I want moderation actions that make no sense for a Bot to be unavailable, so that the interface does not offer to ban the music.

### When things go wrong

32. As a member, I want a Track that will not play to be skipped automatically with the reason shown, so that one deleted video does not stop the music.
33. As a member, I want to be told when the source is refusing requests, so that I understand the problem is not my search term.
34. As a member, I want playback to survive the Music bot briefly losing a connection to one Listener, so that one person's network does not affect everyone.

### Running Voxly

35. As an operator, I want each server's Music bot to exist automatically, so that there is no setup step and no server that mysteriously cannot play music.
36. As an operator, I want to read plainly what the Music bot does and what can break, so that I can decide whether to run it.
37. As an operator, I want to change which upstream client the extractor uses without rebuilding the image, so that I can react when the source changes its rules.
38. As an operator, I want the Music bot to run as a service I can restart on its own, so that a music problem does not take down chat and voice.
39. As an operator, I want the existing read-only filesystem and resource limits preserved, so that adding music does not weaken the deployment's security posture.

### Interface quality

40. As a member sharing my screen while music plays, I want the music panel not to shrink the screen-share area, so that adding music does not degrade what I was already doing.
41. As a Turkish-speaking member, I want every music control and message in Turkish, so that the feature matches the rest of Voxly.
42. As a keyboard-only member, I want to operate search, the Queue and the transport controls without a mouse.
43. As a member using a screen reader, I want each control to announce what it does and what state it is in.

## Implementation Decisions

### Where the Music bot runs

A new workspace runs the Music bot as its own long-lived process, separate from the
Voxly server. It authenticates as an ordinary member and joins voice rooms exactly as a
browser does — one peer connection per Listener. The Voxly server continues to relay
opaque signalling and never touches audio, preserving the peer-to-peer invariant. This
is the subject of ADR-0001, and the repository's architecture rules must be updated to
reference that ADR rather than appearing to forbid this feature.

The bot process does not open the SQLite database. The database runs without WAL mode
and with a synchronous driver, so a second writer would block the Voxly server's event
loop and race it at startup. The bot talks to the server over its existing HTTP and
Socket.IO boundaries like any other client.

### Media path

werift provides the WebRTC endpoint (ADR-0002). Audio is fetched with yt-dlp and
encoded to Opus once by ffmpeg; the resulting encoded stream is written to every
Listener's sender. Adding a Listener costs one more encrypted send, not another
encoder. A fixed conservative bitrate is used with Opus in-band error correction rather
than per-peer rate adaptation, so every Listener hears identical audio.

The bot must supply the same stream-kind descriptor the browser client sends alongside
its offers and answers, implement both the offering and answering sides of negotiation,
handle simultaneous offers, and queue candidates that arrive before the remote
description.

### Bot identity and provisioning

The user record and the presence contract gain a flag marking an account as a Bot. Each
server's Music bot account is created automatically when the server is created,
following the existing pattern that seeds each server's AFK room. A Bot is excluded
from member counts and from moderation actions that assume a person; muting still
applies, because that is how an owner stops the music.

Because an account can occupy only one voice room across the whole deployment, one
account serves one server. This limit is the reason for per-server provisioning.

### State ownership and concurrency

The bot process is the single source of truth for the Queue and playback state. Clients
send acknowledged requests and never mutate their own view optimistically; the bot
applies or rejects each one and broadcasts the resulting state to everyone in the room.
This mirrors how voice membership already works, where the server's acknowledgement is
authoritative and snapshots are broadcast.

Skip requests name the Track they intend to skip. Skipping a Track that is no longer
playing succeeds silently without advancing, so two simultaneous skips remove one Track.
The same targeting applies to removing a queued Track.

Queue state lives in the bot's memory. It does not survive a restart of the bot process,
which is acceptable because a redeploy interrupts voice anyway.

### Sources

YouTube is the only source, reached through yt-dlp for both search and extraction. No
API key is required or used. Two distinct roles are kept separate so that future work
does not require redesign: **resolvers** turn user input into the identity of a Track —
a pasted link, a typed search, and later a pasted Spotify link — while a single **audio
provider** turns that identity into a playable stream. Spotify can never be an audio
provider; its terms and API do not permit rebroadcasting audio, so a future Spotify
feature is a resolver that finds the named Tracks on YouTube.

The upstream client that yt-dlp presents is configurable through the environment, so an
operator can react to changes in the source's anti-automation rules without rebuilding.
The extractor version is pinned at image build time and refreshed by the operator's
normal redeploy; the container's read-only filesystem is not relaxed to allow
self-updating.

### Interface

The music panel is a block in the voice room's existing document flow, placed after the
participant list. It does not float, overlay, or introduce its own scroll region,
because the call surface is the sole scroll owner and the stage must be free to
contract. This is what keeps the panel from competing with screen sharing.

Search presents several results with the first pre-selected. The Set log renders in the
panel and exists only for the duration of the Set.

Transport controls follow the existing control-button pattern, with their labels and
states derived by a pure helper in the same way the microphone and deafen controls
already are. Icons are hand-written inline SVG using `currentColor`; no icon dependency
is added. English and Turkish strings land together.

Only the genuinely shared parts of "being a Bot" are generalised — the flag, how a Bot
renders as a participant, and the existence of a panel slot. No plugin system, registry
or generic bot framework is built, because a good shared abstraction cannot be designed
from a single example.

## Testing Decisions

A good test here asserts externally observable behaviour — what the Queue contains after
a sequence of actions, what a control's label and enabled state are, what the server
acknowledges — and never reaches into internal structure. Tests must survive the media
library being swapped.

### The primary seam: the playback state machine

The bot's decision-making is a pure module: current state plus one event produces new
state plus the effects to perform. Events include a Track being added, a targeted skip,
pause, resume, a Track ending, a Track failing, the last Listener leaving, a Listener
returning, and the Grace period expiring. It performs no input or output; werift,
ffmpeg and yt-dlp are driven by the effects it returns.

Every agreed rule is verified here without audio: skip idempotency under simultaneous
requests, a failed Track being skipped with its reason recorded, the Grace period
surviving a reload and expiring when nobody returns, Requester attribution, and Set log
contents being discarded when the Set ends.

### Reused seam: server realtime tests

Bot-to-server behaviour needs no new machinery. The existing realtime test file already
boots a real server and drives it with a Node Socket.IO client, including acknowledged
voice joins. The Music bot is such a client. Provisioning a Bot account with each
server, the Bot appearing in voice snapshots with its flag, the requirement that a
summoner already occupies the voice room, and an owner's mute silencing the Bot all test
through that seam.

### Reused seam: pure presentation helpers

Queue rows, transport control labels and states, and Set log lines are computed by pure
functions in the web library layer and asserted as data, following the existing pattern
used for voice control presentation and for the voice member selectors. Structural
assertions about new markup and styling follow the existing source and CSS structure
tests, and any new exported declaration referenced by them must be registered in the
shared test-source list.

### Small seam: extractor output parsing

Turning the extractor's JSON output into a Track is a pure function tested against
captured example outputs, including an unavailable video, an age-restricted video and a
live stream. The process spawning around it stays a thin untested adapter.

### Not covered by automated tests

Whether the media path actually produces audible sound cannot be asserted in the Node
test runner. It is verified by a person listening in a browser. This must be proven
before the rest of the feature is built, not after.

## Out of Scope

The following are deliberately excluded from this version and are not partially built:

- Queueing an entire playlist in one action
- Seeking to a position within a Track
- Loop and shuffle
- Automatically playing similar music when the Queue empties
- Normalising loudness across Tracks
- Lyrics
- History of previous days' Sets
- Saved or named playlists
- Spotify links, and any source other than YouTube
- More than one Music bot per server, or one Bot playing into several rooms at once
- A generic bot framework, plugin registry, or second Bot of any kind
- Persisting the Queue across a restart of the bot process
- Continuous integration; verification remains manual, as it is for the rest of the
  repository

Queueing an entire playlist is the most likely first addition afterwards and the
cheapest, because the resolver seam already anticipates it.

## Further Notes

### Build the proof first

Everything in this document rests on an assumption nobody has demonstrated: that a
headless Node peer can join a Voxly voice room and be heard. Research supports it and
the library's own examples match this use case, but that is a report rather than working
sound. The first piece of work should be a throwaway program that authenticates, joins a
voice room, and plays a short checked-in audio file to one browser Listener, confirmed
by ear. If it disappoints, the architecture changes — and finding that out before a
Queue, a panel and a Set log exist on top of it is worth far more than the day it costs.

### Ongoing maintenance is part of the feature

The extractor breaks when the source changes, and fixes arrive in its nightly releases
within days. Expect the music to stop working a few times a year until the operator
redeploys. This is a known, accepted cost rather than a defect, and the operator
documentation should say so plainly.

There is no account to ban, because the bot never signs in. The realistic failure is the
host's address being rate-limited, which is temporary and resolves without intervention.

### Assumptions made while writing this

Two details were not explicitly settled during design and are recorded here as
assumptions rather than decisions, so they are easy to overturn:

- **Removing a queued Track** (story 14) was never discussed. It is included because a
  Queue without removal is frustrating and the mechanism is identical to targeted
  skipping. Cut it if you disagree.
- **Track length shown in the Queue** (story 13) is likewise assumed; the extractor
  returns it, so the cost is display only.
